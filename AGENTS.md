# AGENTS.md

## Scope

This file applies to the whole `ankhorage/templates` repository.

`@ankhorage/templates` owns reusable Ankhorage app templates, category presets,
starter-template selection, manifest generation, and the templates command provider.
Keep it usable as a standalone package by generators, Studio, and other consumers.
Do not turn it into runtime rendering, Studio authoring logic, platform integration,
or application-specific business infrastructure.

## Repository facts

- Package name: `@ankhorage/templates`.
- Runtime: Bun.
- Language: TypeScript, ESM, strict mode.
- Main source root: `src/`.
- Build output: `dist/`.
- Public root export: `src/index.ts`.
- Public CLI/provider export: `src/cli/index.ts`.
- Tests live under `test/`.
- README and API documentation are generated by Paradox. Do not edit generated
  documentation manually; update source documentation and run `bun run docs`.

## Core architectural rules

### Templates owns declarative app seeds

This package owns declarative, reusable inputs for generated Ankhorage apps:

- app-category presets
- starter-template definitions and registry
- routes, screens, content, themes, and splash-screen specifications
- shared manifest-construction helpers
- deterministic template selection and manifest generation
- fixtures used to generate supported example manifests
- `templates.list`, `templates.inspect`, and `templates.create` commands

Avoid:

- runtime component rendering or action execution
- Studio canvas, selection, persistence, or authoring behavior
- Expo-native configuration and platform adapters
- deployment, repository, or infrastructure orchestration
- duplicating contracts owned by `@ankhorage/contracts`
- embedding secrets or environment-specific values in templates

### Package boundaries stay explicit

Use published public APIs from dependency packages. Never import source files from
sibling repositories or rely on a sibling checkout.

- Manifest and app-category contracts belong to `@ankhorage/contracts`.
- Reusable UI components and their public metadata belong to `@ankhorage/zora`.
- Generic runtime behavior belongs to the Ankhorage runtime packages.
- Expo-specific planning and wiring belongs to `@ankhorage/expo-runtime`.
- Studio-specific authoring behavior belongs to `@ankhorage/studio`.

Templates may compose these public contracts into app seeds, but must not redefine
or take ownership of them.

### Category templates stay cohesive

Default category templates live under
`src/templates/starter/categories/<category>/`.

Keep sibling files focused by role:

- `content.ts` owns category content.
- `routes.ts` owns route declarations.
- `screens.ts` owns screen declarations.
- `default.template.ts` assembles the default category template.
- `index.ts` exposes the category's intended internal surface.

A named template variant belongs in its own directory under the category. Keep its
content, routes, screens, and template assembly inside that directory. Extract code
to `src/templates/shared/` only when it is genuinely reusable across templates.

Register new templates explicitly in the starter registry and cover selection,
summary, and manifest generation with tests.

### Generated manifests are deterministic

The same template ID and options must produce the same manifest.

- Do not use current time, randomness, network calls, machine paths, or ambient
  environment state during generation.
- Preserve intentional ordering and sort derived collections when source order is
  not part of the contract.
- Return independent values; do not expose shared mutable template state.
- Keep defaults centralized and make overrides explicit.
- Reject unknown template IDs and invalid options predictably.

### ZORA composition remains declarative

Templates may construct ZORA-backed manifest nodes through supported public
contracts and shared builders. Do not add rendering behavior, component
implementations, or platform-native APIs here.

Prefer shared node builders for repeated structural patterns. Keep category-specific
copy, data, bindings, and screen composition within the owning category or named
variant.

## Public API rules

Keep public exports intentional and small.

When changing published behavior:

1. update the appropriate public entrypoint
2. add or update focused tests
3. add a changeset
4. regenerate documentation when public API docs are affected

Do not expose internal builders merely for test convenience. Do not rely on deep
imports from consumers when a supported root or `./cli` export is appropriate.

## CLI and provider rules

The standalone CLI and Ankh runtime provider must expose the same supported
template operations and use the same underlying command implementation.

- Keep command descriptors, capabilities, and package metadata synchronized.
- Keep structured command output stable and machine-readable.
- Send diagnostics to the appropriate error channel.
- Do not add interactive prompts to provider execution paths.
- Add command and provider tests when command behavior changes.

## Testing rules

Tests must be deterministic and runnable offline.

Cover the narrowest relevant contract:

- registry and selector behavior
- category and named-template manifest generation
- routes, screens, bindings, modules, and auth-flow contracts
- root exports and package metadata
- CLI and runtime-provider behavior
- regression coverage for every corrected template defect

When adding a category or named variant, test both discovery and generated manifest
shape. Prefer structural assertions over broad snapshots that obscure the contract.

## Changesets

Add a changeset when a completed task changes the published API, CLI behavior,
template catalog, generated manifest behavior, defaults, or package metadata.

Repository-only documentation changes, including this file, do not need a
changeset unless they alter release behavior.

## Required verification

Before concluding a code task, run from the repository root:

- `bun run build`
- `bun run lint`
- `bun run test`
- `bun run knip`
- `bun run typecheck`
- `bun run format:check`
- `bunx @ankhorage/ankh doctor validate .`

For public API or generated documentation changes, also run:

- `bun run docs`
- `bun run format:check`

For release or packaging changes, also run:

- `npm pack --dry-run`

If a command fails, report the failure and its cause. Do not weaken validation,
configuration, or types to make a check pass.
